jcode-5sx: agentgrep CPU investigation

Decision: Terminal B, investigation-only after completed paired measurement. No Jcode or agentgrep production candidate was retained.

Evidence

  • Jcode pins agentgrep at upstream revision b01b804008ab0662fa14e6b60b10bff61716e6f1 (tag v0.1.6).
  • The fork's grep path launches one ripgrep subprocess, then rereads every matched file for structure/grouping. Both native and ripgrep post-processing use available_parallelism(), capped only by matched-file count and a small-file threshold. Concurrent calls can therefore multiply CPU workers across tool invocations.
  • Existing profile evidence records targeted grep at 16.410 ms wall and 72.007 ms aggregate CPU, consistent with useful ripgrep plus per-file post-processing rather than a Jcode serialization bug.
  • Completed five randomized rounds over literal, regex, paths-only, type, glob, hidden, no-ignore, and dense fixtures. Candidate output hashes matched baseline for every case.
  • Concurrent attribution at 1/2/4/8 calls measured baseline CPU medians of 10.61/21.23/47.43/102.40 ms and candidate medians of 17.44/32.20/62.91/102.28 ms. Candidate wall medians were slower at every level, so the cap was rejected.
  • Focused Jcode agentgrep tests ran, but four existing tests failed because the current environment's rg-backed fixture execution returned zero matches. Candidate fork tests also showed environment/CWD-dependent failures. The private daemon was built and session creation succeeded, but the follow-up tool call hit a stale debug socket path and was not accepted as daemon evidence.

Why no change landed

The exact-revision baseline and candidate were paired, but the only candidate increased wall time and did not materially reduce CPU. The candidate fork remains unpushed and unpinned; the Jcode worktree and dependency lockfile are unchanged.

Risk assessment

Low Risk

No source, dependency, lockfile, fork, daemon, or shared process was changed.

Medium Risk

Existing aggregate CPU remains high under concurrent grep calls because each call can use all available cores for post-processing. A future candidate must compare CPU, wall time, memory, worker counts, and exact output.

High Risk

Globally serializing searches or blindly reducing workers could regress latency or alter timeout/cancellation behavior. Any fork change must preserve literal/regex matching, ignore/path security, caps, deterministic ordering, and daemon behavior, then be pinned only after paired acceptance.

Follow-up

Run a dedicated fork campaign at the pinned revision with identical fixtures and repeated randomized single/concurrent samples. Prefer adaptive post-processing concurrency over a global inventory cache or unconditional serialization.
